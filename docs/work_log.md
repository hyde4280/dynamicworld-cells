# 作業ログ（セルデータ）

このリポジトリ（dynamicworld-cells）の変更履歴のうち、コミットメッセージだけでは分からない経緯を記録する場所。セルデータの追加・差し替え・形式まわりの記録はここに置き、ローダーやシーン（開発本体）の作業ログとは分けて管理する。

## 2026-11-06 cell005「fujisan」を実寸比＋裾スカートで再生成

ワールドで実物を見たユーザーから「高さと水平の縮尺が合っておらず、鋭角な富士山に見える」と指摘があり、数値で検算したうえで作り直した。

- 検算：切り出し範囲は実寸 約3.99km × 3.98km（水平は約 1/399 に圧縮）。一方で標高幅 1,682m を 8m にフィットしていたため垂直は約 1/210 で、**垂直誇張 約1.9倍**になっていた。DEM実測の斜面（山頂まわり平均 20〜30°）がセル内では 34〜47° になっていた計算。
- 再生成：`tools/gen_dem_cell.py` に `--fit-height 4.2`（この切り出しでの実寸比。山頂高さ 4.2m）を指定。地形そのものは不変。
- 裾の処理：地形シートの外周は地形なりの高さ（外周標高の中央値 2,629m → セル内 約1.35m）に浮いていたため、`--skirt` オプションを新設し、外周から y=0 まで垂直の壁（スカート）を追加して着地させた。スカート分 +1,024 tris で合計 33,792 tris / 17,153 verts。
- アトラス PNG は標高の相対値で塗るため内容不変（md5 一致を確認）。差し替えは OBJ のみ。
- OBJ は 2,722,192 バイトと単独投入の上限に近いため、`cells/cell005.obj.part01` / `.part02` に分割投入し、decode-assets ワークフローで結合・復元する経路を使った。
- 表裏の修正（同日追記）：初版（8m 版）をワールドで見たユーザーから「表裏が逆で内側から見える感じ」との報告。原因は `gen_dem_cell.py` の地形面ワインディングが cellgen.py の規約（法線側から見て CCW、幾何法線＝vn 方向）と逆で、幾何法線が下を向いていたこと。面の並びを (a, d, c)/(a, b, d) に反転して再生成・再投入した（検証：全 32,768 面の幾何法線 y 成分が正、スカート 1,024 面も外向きを確認）。スカート面と vn はもともと規約どおりで変更なし。なお本項の「全体を最低点基準に下げる＋浮く部分はスカート」は、最低点（標高 2,087.7m）が外周の南辺上にあるため、現行の生成（最低点を y=0 に置き外周にスカート）がそのまま該当する。

## 2026-11-05 バイナリ／大容量ファイルの投入経路を新設し、全セルの配信を完了

Muse の GitHub 投入経路は UTF-8 テキスト専用で、PNG が直接上げられず、テキストも 1 リクエスト約 2.6MB 超で上限（413）に当たる制約があった（cell002〜005 の PNG と cell004.obj が「ローカルコミット待ち」になっていた）。代替経路として GitHub Actions の復元ワークフローを新設：

- バイナリは Base64 化した `cells/*.b64` テキストで投入し、Actions が実ファイルへ復元。
- 上限を超えるテキストは `cells/*.part01`〜 に分割投入し、Actions が結合。
- ワークフロー `.github/workflows/decode-assets.yml` は投入経路の権限では置けないため、ユーザー自身が Web から作成（2026-11-05）。以降は `.b64` / `.part` の投入をトリガーに自動実行され、復元結果は bot がコミットする。
- これにより cell002.png / cell003.png / cell004.obj / cell004.png / cell005.png がすべて復元され、Pages 配信を確認（サイズも原本と一致）。cell001〜005 の全セルが OBJ＋PNG のペアで揃った。
- なお `.b64` / `.part` ファイルは投入の原票としてリポジトリに残る（実ファイルと二重管理になるため、実ファイルを直接編集した場合は `.b64` 側の再投入で上書きされる点に注意）。
- cell005 の項に書いた「PNG はローカル側のコミット待ち」は、この仕組みで解消済み。

## 2026-11-09 cell006〜009 の Z ファイト修正（共面重なり面の除去）
